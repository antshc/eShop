# eShop Overview

eShop is a .NET 10 reference e-commerce application ("AdventureWorks") built as a services-based architecture orchestrated by Aspire. Services (Catalog, Basket, Ordering, Identity, Webhooks, payment/order processors) communicate over HTTP/gRPC and a RabbitMQ-backed integration-event bus, with Blazor (WebApp) and .NET MAUI (HybridApp, ClientApp) front ends.

## Crosscutting Concepts

This section describes crosscutting concepts (practices, patterns, regulations, recurring approaches). They preserve architectural consistency.

| Concept | Trigger condition | Default |
|---------|-------------------|---------|
| **[Reliable Integration Event Publishing](docs/concepts/str-reliable-integration-event-publishing.md)** | integration event, outbox, publish event after state change, event bus, RabbitMQ, event log, order status event, event consumer subscription | A service that changes its own database state and publishes an integration event writes the event to the integration event log in the same transaction and relays it to the event bus after commit; publishers with no owned state change publish directly. |
| **[Service Defaults and Observability](docs/concepts/ops-service-defaults-and-observability.md)** | new service or worker, telemetry, OpenTelemetry, logging, tracing, metrics, health check, service discovery, resilience handler, OTLP | Every ASP.NET-hosted deployable registers the shared service defaults; use the basic variant only when it makes no outgoing HTTP calls; export OTLP only when the endpoint setting is set. |
| **[Service Authentication and Authorization](docs/concepts/ops-service-authentication.md)** | sign in, login, OIDC, Identity.API, JWT bearer, access token, protect endpoint, RequireAuthorization, anonymous access, webhook token | Browser apps use cookie plus OIDC code flow and forward the user's access token; protected APIs validate JWT bearer through the shared default authentication and require authorization on their route groups. |
| **[Schema Migration and Persistence Stores](docs/concepts/ops-schema-migration-and-persistence.md)** | database, new table, schema change, EF migration, seed data, startup migration, PostgreSQL, Redis, new service data store | A database-owning service uses its own PostgreSQL database and EF context and applies migrations and seeding at startup through the shared migration hosted service; per-user ephemeral keyed data goes to Redis. |
| **[Inter-Service Communication and API Versioning](docs/concepts/str-inter-service-communication.md)** | service calls service, new endpoint, HTTP client, gRPC, API version, breaking API change, mobile BFF, webhook callback | Synchronous calls use versioned HTTP/JSON through typed clients over service discovery; the basket uses gRPC; cross-service state changes are integration events; MAUI apps go through the mobile BFF. |
| **[Error Handling and Request Validation](docs/concepts/ops-error-handling-and-validation.md)** | validation, invalid input, error response, ProblemDetails, domain exception, retry, resilience, idempotent command, MediatR behavior | Reject bad input at the API boundary with a 4xx problem response; domain invariants throw domain exceptions; transient faults rely on the shared resilience handler, EF execution strategy and broker retry; use FluentValidation behaviors only where a MediatR command pipeline exists, otherwise model validation. |
| **[Test Strategy](docs/concepts/ops-test-strategy.md)** | write tests, new test project, unit test, functional test, integration test, e2e, Playwright, test fixture, test authentication | Logic and configuration tests use MSTest with NSubstitute; container-backed API functional tests use xUnit with an Aspire fixture; browser flows use Playwright against the AppHost. |
| **[Configuration and Secrets](docs/concepts/ops-configuration-and-secrets.md)** | configuration value, connection string, service URL, options class, appsettings, secret, User Secrets, environment variable, AppHost parameter | The AppHost supplies connection strings and URLs; service tunables are typed options bound from a dedicated section; secrets live in Aspire secrets or User Secrets and are never committed. |
| **[Build and Package Management](docs/concepts/ops-build-and-package-management.md)** | add NuGet package, package version, new project, Directory.Build, SDK version, solution file, CI build, MAUI build | Package versions live only in the central package file, compiler policy in the shared build properties, SDK and test runner in the SDK configuration; CI builds the web solution filter and MAUI projects build in their own workflow. |
